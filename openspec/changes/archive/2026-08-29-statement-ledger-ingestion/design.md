# Design: statement-ledger-ingestion

Status: accepted (designer phase). Backend-only; no UI.

## Context

The backend today has exactly one data path: the document/asset ingestion pipeline from
`invoice-warranty-asset-flow` (v3). It is committed and working: a flat four-layer Go
module (`module procrastinator-backend`) — `commons/` (shared kernel: `entity`, `repo`,
`parse`, `tenant`, plus `dates.go`/`normalize.go`), `core/` (`identity`, `ingest`),
`infra/` (`postgres`, `llm`, `filestorage`), `api/` (server/handlers/dto, `httpx`,
`cmd/procrastinator`), and a top-level `config/`. The persistence boundary is a single
generic `repo.Repository[T]` with functional `Option`s (`repo.Tenant`/`Where`/`Limit`/
`Offset`/`OrderBy`), a `repo.Repos`/`repo.Factory` bundle (currently `Assets`, `Sources`,
`Documents`) and a `factory.InTx(ctx, fn(ctx, *Repos))` transaction mechanism
(`procrastinator-backend/commons/repo/factory.go`,
`procrastinator-backend/infra/postgres/factory.go`). Money is represented as exact-decimal
strings in Go (`Asset.Price *string`, `procrastinator-backend/commons/entity/asset.go`),
`numeric` in SQL, and JSON strings in the API. IDs are generated by the DB
(`gen_random_uuid()`, `procrastinator-backend/infra/postgres/repository.go`). Tenant
scoping is fail-closed: `repo.Tenant(tid)` at the call site, context fallback, otherwise
`tenant.ErrNoTenant` (`procrastinator-backend/commons/tenant/tenant.go`).

**The gap (CRIT-D-01):** an invoice's price and currency are captured but connect to
nothing — there is no ledger, no account, no money movement. The design docs require a
minimal finance ontology *derived from research* before any finance code. Real life
produces bank statements, wallet statements, and receipts that describe the same money
from different angles; without a canonical ledger and a disciplined import path each
stays an isolated fact. This is a solved shape in the research corpus (Firefly III
accounts + withdrawal/deposit/transfer movements + external-ID dedup; LifeStack
deterministic import batches with source retention + rollback hooks; Paperless-ngx
preview/classify before persist), so this design reuses those patterns.

**Forces in tension:**
- **Atomicity vs. the existing tx mechanism.** Commit must create all valid-line
  movements or none (ST-008). The only tx mechanism is `factory.InTx`, which hands the
  callback a `*repo.Repos`. Finance writes therefore need finance repos *inside* `Repos`.
- **Determinism vs. concurrency.** Duplicate classification must be deterministic
  (same file + same ledger state → same statuses), but concurrent commits could race on
  the same document link.
- **Compatibility with the in-flight change.** `invoice-warranty-asset-flow` owns
  `Repos`/`Factory`, `infra/postgres/factory.go`, and `main.go`. This change must build on
  it without breaking the refactor, and must not edit `document-ingestion` behavior.
- **No float.** Money must be exact (spec `Money representation`); the existing
  `*string`/`numeric` convention is the proven path.

## Goals / Non-Goals

**Goals** — the `financial-ledger` capability (accounts, expense/income/transfer
movements, exact-decimal money, derived balances, manual entry, reversible
movement–document links with conflict retention, immutability rules, tenant scoping) and
the `statement-import` capability (CSV/text-PDF import batches: source retention, parse,
per-line preview, deterministic dedup, atomic idempotent commit, discard, auto-link,
tenant scoping) as additive `/api/finance/*` endpoints on the existing flat architecture.

**Non-Goals** (hard constraints, SPX-003 — implementers MUST NOT add these):
- No UI screens; no reconciliation UX; no net worth / investments / loans / budgets / goals.
- No FX / multi-currency movements (a transfer across currencies is not representable).
- No categories/allocations, no debts/receivables/settlements, no OCR of image-only
  statement PDFs, no connector auto-fetch, no rollback of committed batches, no reversal/
  correction of committed imported movements.
- No change to the `document-ingestion` asset pipeline, the existing
  `/api/documents`/`/api/assets` endpoints, the LLM prompt, or the existing tables
  (`sources`, `assets`, `documents`).
- No `multitenancy` / `backend-platform` spec deltas (stated inside the two new
  capabilities to avoid a merge conflict with the in-flight change).

## Decisions

### D1: Two bounded contexts under the existing four layers

The finance domain is split into two bounded contexts (DDD-001/002), both in `core/`:

- **`financial-ledger`** (`core/ledger/`) — accounts, money movements, derived balances,
  and movement–document links. Upstream context; owns all movement writes and the link
  rules.
- **`statement-import`** (`core/statement/`) — import batches, lines, upload/parse/
  classify/commit/discard, and auto-link orchestration. Depends on `financial-ledger`
  (it creates movements and applies auto-links). `financial-ledger` does not import
  `statement-import` (MOD-005: specific → general).

Both contexts import `commons/` only — never `net/http`, `pgx`, or any `infra/` package
(the existing layering rule, verified via `go list -deps ./core/...`). Entity-specific
persistence stays concrete in `infra/postgres` and is consumed through narrow consumer-side
interfaces defined in `core/` (the `AssetStore`/`documentLister` precedent from
`invoice-warranty-asset-flow` D7).

**Rejected alternative:** a single `core/finance` package mixing ledger + import.
Rejected — the two contexts have different vocabularies (movement vs. batch/line) and
different lifecycles; one package would be a god package (MOD-010).

### D2: Data model — one goose migration, four tenant-scoped tables

One new versioned migration `procrastinator-backend/migrations/00004_finance.sql` (renumbered
from 00002 to 00004 during implementation: the parallel in-flight `multi-tenant-isolation`
change claimed goose versions 00002/00003) adds the
finance tables. Existing tables are untouched. It follows the committed schema's
conventions (not the fuller PoC in `docs/Life_Manager_DB_Schema.md`): `uuid PRIMARY KEY
DEFAULT gen_random_uuid()`, `tenant_id text NOT NULL`, `numeric` for money, `char(3)` for
currency, `timestamptz ... DEFAULT now()`.

```sql
-- +goose Up
CREATE TABLE financial_accounts (
    id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id         text NOT NULL,
    name              text NOT NULL,
    account_type      text NOT NULL CHECK (account_type IN ('bank','wallet','cash','credit_card')),
    currency          char(3) NOT NULL,
    institution       text,
    external_descriptor text,
    created_at        timestamptz NOT NULL DEFAULT now(),
    updated_at        timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_fin_accounts_tenant ON financial_accounts (tenant_id);

CREATE TABLE money_movements (
    id                     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id              text NOT NULL,
    kind                   text NOT NULL CHECK (kind IN ('expense','income','transfer')),
    amount                 numeric NOT NULL CHECK (amount > 0),
    currency               char(3) NOT NULL,
    occurred_on            date NOT NULL,
    recorded_at            timestamptz NOT NULL DEFAULT now(),
    description            text NOT NULL,
    norm_description       text NOT NULL,
    origin                 text NOT NULL CHECK (origin IN ('manual','import')),
    source_account_id      uuid REFERENCES financial_accounts(id),
    destination_account_id uuid REFERENCES financial_accounts(id),
    -- import provenance (NULL for manual)
    import_batch_id        uuid,
    import_line            int,
    external_reference     text,
    -- document link (at most one document per movement, at most one movement per document)
    linked_document_id     uuid,
    link_creator           text CHECK (link_creator IN ('manual','auto')),
    link_conflicting       boolean NOT NULL DEFAULT false,
    created_at             timestamptz NOT NULL DEFAULT now(),
    updated_at             timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT chk_kind_accounts CHECK (
        (kind = 'expense'  AND source_account_id IS NOT NULL AND destination_account_id IS NULL)
        OR (kind = 'income' AND source_account_id IS NULL AND destination_account_id IS NOT NULL)
        OR (kind = 'transfer' AND source_account_id IS NOT NULL AND destination_account_id IS NOT NULL
            AND source_account_id <> destination_account_id)
    )
);
CREATE INDEX idx_movements_tenant      ON money_movements (tenant_id);
CREATE INDEX idx_movements_src_acct    ON money_movements (tenant_id, source_account_id)     WHERE source_account_id IS NOT NULL;
CREATE INDEX idx_movements_dst_acct    ON money_movements (tenant_id, destination_account_id) WHERE destination_account_id IS NOT NULL;
CREATE INDEX idx_movements_occurred    ON money_movements (tenant_id, occurred_on);
CREATE INDEX idx_movements_extref      ON money_movements (tenant_id, external_reference)    WHERE external_reference IS NOT NULL;
CREATE UNIQUE INDEX uq_movement_linked_doc ON money_movements (tenant_id, linked_document_id) WHERE linked_document_id IS NOT NULL;

CREATE TABLE import_batches (
    id                       uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id                text NOT NULL,
    state                    text NOT NULL CHECK (state IN ('preview','committed','discarded')),
    account_id               uuid NOT NULL REFERENCES financial_accounts(id),
    source_id                uuid NOT NULL REFERENCES sources(id),
    filename                 text NOT NULL,
    format                   text NOT NULL CHECK (format IN ('csv','pdf')),
    line_count_valid         int NOT NULL DEFAULT 0,
    line_count_duplicate     int NOT NULL DEFAULT 0,
    line_count_possible_dup  int NOT NULL DEFAULT 0,
    line_count_error         int NOT NULL DEFAULT 0,
    created_at               timestamptz NOT NULL DEFAULT now(),
    updated_at               timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_import_batches_tenant ON import_batches (tenant_id);

CREATE TABLE import_lines (
    id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id          text NOT NULL,
    batch_id           uuid NOT NULL REFERENCES import_batches(id) ON DELETE CASCADE,
    line_ref           int NOT NULL,
    raw_line           text NOT NULL,
    occurred_on        date,
    amount             numeric,
    direction          text CHECK (direction IN ('in','out')),
    description        text,
    norm_description   text,
    external_reference text,
    status             text NOT NULL CHECK (status IN ('valid','duplicate','possible-duplicate','error')),
    error_reason       text,
    created_at         timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_line_ref UNIQUE (batch_id, line_ref)
);
CREATE INDEX idx_import_lines_tenant ON import_lines (tenant_id);
CREATE INDEX idx_import_lines_batch  ON import_lines (tenant_id, batch_id, line_ref);

-- +goose Down
DROP TABLE IF EXISTS import_lines;
DROP TABLE IF EXISTS import_batches;
DROP TABLE IF EXISTS money_movements;
DROP TABLE IF EXISTS financial_accounts;
```

Design notes:
- **No `uq_account_tenant_name`.** The PoC schema's per-tenant account-name unique
  constraint is intentionally dropped — the `financial-ledger` spec allows duplicate
  account names. `norm_description` mirrors the existing `norm_*` convention
  (`commons/entity/asset.go`) so the content fingerprint can be indexed/compared.
- **Link as columns, not a junction table (D9).** A movement links to at most one document
  (single `linked_document_id` column, inherent) and a document to at most one movement
  (the partial unique index `uq_movement_linked_doc`). A junction table was rejected as
  extra machinery for a 1:1 relationship (CRIT-D-10).
- **Kind vocabulary** maps the PoC `debit`/`credit`/`transfer` to the spec's
  `expense`/`income`/`transfer`; `chk_kind_accounts` enforces the kind/account-shape
  rules at the DB as defense-in-depth (the service also validates, for precise 400/404).

### D3: Extend `repo.Repos`/`repo.Factory` additively; entity-specific queries stay concrete

`repo.Repos` and `repo.Factory` gain four fields (purely additive, existing fields
untouched): `Accounts Repository[entity.FinancialAccount]`, `Movements
Repository[entity.MoneyMovement]`, `ImportBatches Repository[entity.ImportBatch]`,
`ImportLines Repository[entity.ImportLine]`. `infra/postgres` builds the four concrete
repos (each a `pgRepository[T]`) and populates them in `NewFactory` (pool-bound) and in
the `InTx` callback (tx-bound).

**Why extend the shared bundle (and not a separate finance bundle):** the atomic commit
needs tx-bound access to `Movements` + `ImportBatches`, and the upload needs tx-bound
`ImportBatches` + `ImportLines`. The only tx mechanism is `factory.InTx` → `*repo.Repos`,
so the finance repos must live in `Repos` to be tx-bound. This is the one cross-cutting
touch to the in-flight change's files, and it is **purely additive** (new fields; the
refactor's generic mechanism is untouched), so it is merge-conflict-safe.

Entity-specific queries are **not** on the generic interface; they are concrete postgres
methods consumed via consumer-side interfaces in `core/` (the `AssetStore`/`documentLister`
pattern):

- `BalanceForAccount(ctx, accountID, opts...) (string, error)` — derived balance as an
  exact decimal string: `COALESCE(SUM(amount) FILTER (WHERE destination_account_id=$a),0)
  - COALESCE(SUM(amount) FILTER (WHERE source_account_id=$a),0)`.
- `MovementsForAccount(ctx, accountID, opts...) ([]entity.MoneyMovement, error)` —
  movements where `source_account_id = $a OR destination_account_id = $a` (the generic
  `Where` is AND-only, so an OR needs a concrete query).
- `LinkCandidates(ctx, amount, currency, opts...) ([]entity.Document, error)` — documents
  where `extracted_fields->>'price' = $amount AND extracted_fields->>'currency' = $currency
  AND NOT EXISTS (a same-tenant movement with `linked_document_id = doc.id`)`.

**Rejected alternative:** a separate `FinanceFactory`/`FinanceRepos` bundle with its own
tx. Rejected — it fragments the transaction mechanism and still needs the `Documents` repo
in the commit for auto-link, so it would be a parallel tx factory for no isolation benefit.

### D4: Money as exact-decimal strings; `commons.ParseDate` for dates

Movement `Amount` is `string` (required, exact decimal), `Currency` is `string` (ISO 4217).
Optional money (none at the moment; import-line `Amount` is `*string`) uses `*string`.
SQL is `numeric`; JSON is a string. No float anywhere (spec `Money representation`). A
small `commons/money.go` adds `IsValidAmount` (positive, exact decimal, rejects float/
`"12.5.3"`/`0`/negative), `IsValidCurrency` (3 letters), and
`NormalizeDescription(s) = strings.ToLower(CollapseWhitespace(s))` (reusing
`commons.CollapseWhitespace`, `procrastinator-backend/commons/normalize.go`). `occurred_on`
parsing reuses `commons.ParseDate` (`procrastinator-backend/commons/dates.go`).

### D5: Statement parsing — stdlib CSV; pure-Go PDF text extractor behind an interface

Format is determined by **content sniffing of the bytes**, not the client header:
`%PDF-` magic → `application/pdf`; a text/CSV heuristic → `text/csv`; anything else →
`415 Unsupported Media Type`. Parsing is pure and testable, in `core/statement/`:

- **CSV** — stdlib `encoding/csv` (no new dependency). Rows → raw line strings.
- **PDF (text layer only)** — the PDF text is extracted by a consumer-side interface
  `core/statement.PDFTextExtractor` (`ExtractText(data []byte) (string, error)`) whose
  concrete is `infra/pdftext` using `github.com/ledongthuc/pdf` (pure Go, no CGO). The
  extracted text is split into lines. An image-only/scanned PDF yields no text layer →
  zero parseable lines → `422` (OCR is out of scope).

The one new dependency is `github.com/ledongthuc/pdf` (additive to `go.mod`).

**Rejected alternatives:** shell out to `pdftotext` (poppler) — a system dependency that
breaks the pure-Go, Docker-testable convention. Reuse the LLM to "read" the PDF — the
import path must be deterministic and the LLM is for document classification, not line
parsing; it would also blur the OCR boundary.

### D6: Statement source retention — a dedicated statement store, document store untouched

A new file `infra/filestorage/statement.go` adds a statement-oriented store
(`StatementStorage`) that sniffs CSV/PDF, writes the bytes to the storage dir, and returns
an `entity.Source` **with the original filename retained** (the existing
`filestorage.Storage.Put` sets `Filename` to the UUID and rejects CSV, so it cannot be
reused without changing `document-ingestion` behavior — which is forbidden). It is consumed
through a consumer-side interface `core/statement.StatementSourceStore`
(`Store(ctx, originalName string, data []byte) (entity.Source, error)`). The Source row is
written **before** parsing so it survives a later parse failure / 422 (spec `Statement
source retention`). `infra/filestorage/storage.go` is not modified.

### D7: Deterministic duplicate detection — pure function at upload/preview

Classification is a pure function `classify(lines []ParsedLine, existing
[]entity.MoneyMovement) []ParsedLine` in `core/statement/`, run before the batch is
persisted (so preview creates no movements and changes no balance). `existing` is fetched
once via `MovementsForAccount` for the target account, scoped to the uploading tenant.
Per line, in priority order:
1. **`duplicate`** — the line carries an external reference equal to the external reference
   of an already-committed movement on the same account+tenant, **or** it repeats an
   earlier line in the same batch (same external reference or same content fingerprint).
2. **`possible-duplicate`** — otherwise, its content fingerprint `(occurred_on, amount,
   NormalizeDescription(description))` equals the fingerprint of an existing movement on
   the same account+tenant of any origin.
3. **`valid`** — otherwise. A line from which date, amount, and description cannot all be
   extracted is `error` (with a reason) and does not block the others.

Determinism: same file + same ledger state → same statuses. Re-importing a committed
statement yields all-`duplicate` (its external references / fingerprints are all present
in the committed movements). Classification considers **only** the uploading tenant's
movements (spec `Tenant scoping of import data`).

### D8: Commit — atomic movement write, idempotent re-commit, idempotent auto-link

`POST /api/finance/import-batches/{id}/commit`:
- **`discarded` batch → `409`.** **`committed` batch → idempotent `200`** with the same
  summary (recomputed from the batch's existing movements) and the auto-link step re-applied
  (idempotent). **`preview` batch →** one transaction `factory.InTx` that (a) creates one
  `MoneyMovement` per `valid` line — all or none — with origin `import`, kind
  `expense`/`income` by the line's direction (imports never create transfers), the target
  account as source (out) or destination (in), the account's currency, the line's amount /
  occurred date / description / external reference, and provenance (`import_batch_id`,
  `import_line`); and (b) transitions the batch to `committed` with its per-status counts.
- **Auto-link** (spec `Auto-linking of committed movements`) runs as a separate
  **idempotent** step after the movement tx: for each newly created, not-yet-linked
  movement, `LinkCandidates(amount, currency)`; if **exactly one** unlinked candidate
  exists, set the movement's `linked_document_id` + `link_creator = "auto"` (never
  conflicting, because candidates are exact matches). `duplicate`/`possible-duplicate`/
  `error` lines create no movement; a client wanting a skipped line uses the manual API.

**Why auto-link is a separate idempotent step, not in the movement tx:** the candidate
query is a JSONB + `NOT EXISTS` query the generic `Repository[T]` cannot express, and making
it tx-bound would force a parallel tx factory (rejected in D3). Running it sequentially on
the committed state is correct for within-batch dedup (a link committed for one movement
removes the document from later candidates) and the partial unique index
`uq_movement_linked_doc` is the backstop for cross-request races (a losing auto-link is
simply skipped). Idempotent re-application on re-commit makes it recoverable after a crash
between the movement tx and the link step (ST-005/ST-008).

### D9: Link model, idempotency, and conflict retention

A movement's link lives in `money_movements` columns (D2). `POST /api/finance/movements/{id}/link`
(`document_id` body) semantics, evaluated in order:
- unknown movement / unknown document / cross-tenant document → `404` (no link).
- movement already linked to a **different** document → `409`; document already linked to a
  **different** movement → `409`.
- movement already linked to the **same** document → idempotent `200` no-op.
- otherwise create the link with `link_creator = "manual"` and compute the conflict flag.

**Conflict retention (spec `Link conflict retention`):** if the document carries an
extracted price **and** currency (`documents.extracted_fields`) and either disagrees with
the movement's amount/currency, the link is marked `link_conflicting = true` and **both**
values are retained unchanged (no overwrite of either side, no silent unlink). Agreeing
values → no conflict. A document with no extracted price/currency → no conflict.
`DELETE /api/finance/movements/{id}/link` is idempotent (`204`, including for an unlinked
movement); unknown movement → `404`. Link create/remove never mutates the movement's
amount/currency/occurred/kind/accounts nor the document.

### D10: Tenant scoping and fail-closed persistence

`tenant_id` on all four tables. Every repo call passes `repo.Tenant(tid)`; `tid` is
resolved once from the request context (fail-closed). A persistence operation with no
resolvable tenant returns `tenant.ErrNoTenant` and runs no query (the existing
`resolveTenant` behavior, `procrastinator-backend/infra/postgres/repository.go`). No API
response exposes another tenant's data; foreign-tenant account/movement/batch ids behave
as non-existent (`404`); duplicate detection is scoped to the uploading tenant.

### D11: Error and status mapping

`core/` returns sentinel errors; `api/` maps them (the `writeProcessError` precedent in
`procrastinator-backend/api/handlers.go`):

| Condition | Sentinel | HTTP |
|---|---|---|
| upload > `MaxStatementBytes` | `ErrTooLarge` | `413` |
| sniffed type not CSV/PDF | `ErrUnsupportedType` | `415` |
| accepted file, zero parseable lines (incl. image-only PDF) | `ErrNoLines` | `422` |
| parsed lines > `MaxStatementLines` | `ErrTooManyLines` | `422` |
| invalid transition (commit/discard of a terminal batch, delete of imported movement) | `ErrConflict` | `409` |
| invalid body / field (type, amount, description, core-field edit) | (validation) | `400` |
| unknown account / movement / batch / document / cross-tenant | `repo.ErrNotFound` | `404` |
| missing/invalid `X-Tenant-ID` (defensive) | `tenant.ErrNoTenant` | `401` |

### D12: Config and quantitative bounds

`config.Config` gains `MaxStatementBytes` (env `PROCRASTINATOR_MAX_STATEMENT_BYTES`,
default `52428800` = 50 MiB) and `MaxStatementLines` (env `PROCRASTINATOR_MAX_STATEMENT_LINES`,
default `100000`). The size limit is enforced twice — at the HTTP layer
(`http.MaxBytesReader`) and in the service — mirroring the document upload. The parse/classify
budget is a documented 60 s for any in-bounds file (verified by the 100k-line CSV
integration test, not a hard runtime timeout).

## Interactions and data flow

**Account/movement (ledger, pool-bound, no tx):**
```
handler → resolve tid (ctx, fail-closed)
  create account:  validate(type,name,currency) → Accounts.Create
  get account:     Accounts.Get → 404 if ErrNotFound ; BalanceForAccount(tid, acct) → JSON
  create movement: validate(amount>0, currency, description, kind shape,
                        accounts exist (404) + currency match) → Movements.Create(origin=manual)
  link:            Movements.Get + Documents.Get (404s) → 409/idempotent checks
                        → compute conflict from doc.extracted_fields → Movements.Update(link fields)
```

**Statement upload (preview):**
```
handler: MaxBytesReader(413) → read "file" + "account_id" (400 if missing)
service: size check (ErrTooLarge)
  → sniff type (ErrUnsupportedType if not csv/pdf)
  → StatementSourceStore.Store (Source retained even if parse later fails)
  → Accounts.Get(account_id) (404 if unknown)
  → parse → []RawLine (CSV: encoding/csv ; PDF: PDFTextExtractor → split) ; zero → ErrNoLines
  → line count > MaxStatementLines → ErrTooManyLines
  → extractFields per line (error lines carry a reason)
  → existing = MovementsForAccount(tid, account)  [uploading tenant only]
  → classify(lines, existing)  (pure; duplicate / possible-duplicate / valid)
  → InTx: ImportBatches.Create(preview) + ImportLines.Create(each)   (atomic batch+lines)
  → 201 { batch, lines+statuses }
```

**Commit:**
```
service: ImportBatches.Get (404)
  discarded → ErrConflict (409)
  committed → summary = recompute(batch) ; applyAutoLinks(batch) ; 200 summary
  preview   → InTx: for each valid line: Movements.Create(origin=import, kind by direction,
                  currency=account.currency, provenance) ; ImportBatches.Update(committed, counts)
              applyAutoLinks(batch)   (idempotent; LinkCandidates → exactly-one → Movements.Update(link, auto))
              → 200 { created, skipped }
```

**Auto-link (idempotent):** for each import-origin movement of the batch not already linked:
`cands = LinkCandidates(tid, mv.amount, mv.currency)`; `len(cands)==1` → set
`linked_document_id`, `link_creator="auto"`; else no link. The partial unique index
guarantees a document is linked from at most one movement even under races.

## Failure modes (CRIT-D-08)

- **Parse failure / image-only PDF:** Source retained (written first), no batch, `422`
  (or `415`/`413` per D11). No movements, no balance change.
- **Partial commit:** the movement tx rolls back on any error — no partial batch of
  movements, batch stays `preview` (ST-008). Verified by an integration test that injects
  a mid-tx failure.
- **Crash between movement tx and auto-link:** re-commit re-applies auto-links
  idempotently (D8); movements are never duplicated (re-commit is a no-op on the tx path).
- **Concurrent auto-link on one document:** `uq_movement_linked_doc` rejects the second;
  the loser skips (no link). Deterministic single-candidate rule still holds for
  non-racing commits.
- **LLM not involved** in the import path (no LLM dependency/failure mode for statements).
- **Concurrency on the balance:** derived on read (no stored balance to race); no
  check-then-act on money.

## NFRs (CRIT-D-09)

- **Size:** ≤ 50 MiB per upload (configurable; `413` above).
- **Line count:** ≤ 100 000 lines per batch (`422` above).
- **Latency budget:** parse+classify for any in-bounds file ≤ 60 s (checked by the 100k-line
  integration test). Balance is an indexed aggregate; dedup is one in-memory pass over the
  target account's movements.
- **Tenant isolation:** fail-closed; foreign ids behave as `404`; cross-tenant dedup is
  impossible (scope-limited fetch).

## Risks / Trade-offs (CRIT-D-04)

- **Additive edit to `Repos`/`Factory`/`infra/postgres/factory.go`/`main.go`** — the minimal,
  conflict-safe bridge to the in-flight change. Negative: a (small) shared-file touch the
  proposal's "touches none of that change's files" idealizes away; accepted because the
  atomic commit *requires* tx-bound finance repos and the edit adds fields without
  altering the generic mechanism.
- **PDF library (`ledongthuc/pdf`)** — pure Go but a new dependency; some exotic PDFs may
  extract imperfect text (falls back to `error` lines, not silent data loss). Negative
  accepted over a poppler system dependency.
- **Auto-link not in the movement tx** — a crash can leave committed-but-unlinked
  movements until the next (idempotent) re-commit; the link is best-effort by spec.
  Accepted for determinism + no parallel tx factory.
- **Balance as a read-time aggregate** — O(indexed sum); no materialized balance to keep in
  sync. Fine at PoC scale; a materialized/`derived_state` balance can be added later without
  API change.
- **Full-entity `Update` for link/description** — re-sets unchanged columns (harmless);
  core-field immutability is enforced in the service *before* any update (D9/D11), so the
  DB `Update` never sees a core-field change from these endpoints.
